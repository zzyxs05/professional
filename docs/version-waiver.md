# version-waiver · 规则包版本错配的成因与消除【review】

> 性质：review ｜ 版本：v1.0 ｜ 状态：复核中

> 关联：变更台账 `docs/changes.md`；实现 `core/registry.py`、`core/dexscan.py`；评价输出 `review/evaluation/`；新正本 `evidence/RUN-20261124-*/`。

## 1. 问题是怎么来的

评价器有一条硬规则（SKILL.md §5、rubric interpretation）：**旧证据不判新版本**。契约要求 `report.versions.rule_pack` 与批准契约的 `rule_pack_version` 一致，否则 `version_check.mismatch=true`，该项判 `INSUFFICIENT_EVIDENCE`。

2026-11-18 评价时：
- 6 个 RUN 正本（`RUN-20261015-*`）由规则包 **0.1.3** 生成；
- 当时的契约已是 **0.1.4**；
- 于是 6 份评价输出全部 `mismatch=true` → 顶层 `INSUFFICIENT_EVIDENCE`。

这是**机械结论，不是评价器 bug**，也不是可以通过放宽契约绕过的检查。

## 2. 版本之间到底改了什么（都是什么性质）

| 版本 | 变更 | 性质 | 对历史正本结论的影响 |
|---|---|---|---|
| 0.1.3 → 0.1.4 | `core/dexscan.py::_read_string_at` 跳过 ULEB128 长度前缀再读字符串（OBS-5）；`changes.md` C1—C9 | **数据层读取修复**，不改任何规则的检测点、误报口径、档位上限 | `changes.md` C6 记录：影子重跑 84/84、硬错 0、噪声 0，**与 0.1.3 成绩单逐字节一致**；正常路径结论不变，仅降级路径 R-CODE-01 由恒不命中变为可给弱证据 |
| 0.1.4 → 0.1.5 | 结论全量化、B1/B2 prompt 数据边界、敌对样本防御（`changes.md` 第一次审查节） | **报告形态与韧性**变更 | 每条判点都要出结论，报告变长；已签历史正本不改写 |
| 0.1.5 → 0.1.6 | B3 汇总判据修正、12 项 Android 12/13+ 权限使用模式补齐（`changes.md` 第二次审查节） | **汇总统计 + 规则表扩充** | 靶场未声明这些新权限，84 判点不受影响 |

**关键点**：0.1.4 相对 0.1.3 的修复落在 `core/dexscan.py::_read_string_at`——旧实现把 ULEB128 长度字节当成字符串首字节，使 `strings`/`type_descriptors`/`method_refs` 带控制字符前缀；修复只改"怎么读字符串"，不改规则判定条件（见 `changes.md` C2/C3/C8）。

## 3. 错配是怎么消除的（做对了什么）

T-M5-10 的完成标志是"评价不再报版本错配"。实现路径选的是**重跑新正本**，而不是"写豁免放行旧正本"：

1. 该批次处理时规则包已到 **0.1.6**（当前为 0.1.7，见 `core/registry.py::RULE_PACK_VERSION`）；
2. 2026-11-24 用 0.1.6 重跑 6 个样本，生成 6 个新正本 `RUN-20261124-*`；
3. 新正本的 `meta.json.rule_pack` 与 `report.json.versions.rule_pack` 均为 0.1.6，与内部契约一致；
4. 6 份新评价输出（`EVAL-20261124-0815*`）实测 `version_check.mismatch = false`。

> 该结论当时的证据是 6 份 EVAL 的 `version_check` 字段；这批 EVAL 文件已于 2026-11-26 清理，仓库内不再保留；它们是测试产物，不纳入签署台账。

## 4. 历史正本怎么处理（不改写）

- 6 个 `RUN-20261015-*` 正本**保持原样**，不改写、不补造版本号；
- 它们与当前契约的版本错配事实**继续存在**，评价它们仍会 `mismatch=true` —— 这是正确行为，不掩盖；
- 新批次正本与新评价输出另起一批，通过 `docs/signoff.md` 登记切换（登记批次确认，见 T-M5-14）。

## 5. 没有做的事（如实列）

- 仓库中没有 0.1.3 时期的成绩单文件（`review/truth_result_0_1_4.json` 是 0.1.4 的）；"0.1.3 与 0.1.4 逐字节一致"是 `changes.md` C6 的历史记录，本文引用它，**不声称本次重新逐字节核验过 0.1.3 成绩单**。
- 本文不构成豁免批准、不构成签署；是否把新批次登记为评价正本，由本组具名人决定。
- 0.1.4 的 OBS-5 修复在 `TASKS.md` 仍标"已实施，待具名人复核"，本文不改变该状态。
