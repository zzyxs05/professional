# ADR-0008 · 目标用户：以"复核者"为主用户，而不是"扫描者"

- 状态：已采纳
- 决策人：周宗正（起草）、余俊辉（复核）
- 关联：`requirements.md` §1/§3、`brief.md` §2、`specification.md` §4

## 背景

"目标用户"这个问题如果不回答，后面所有取舍都没有依据：报告该写长还是写短、结论该保守还是激进、要不要做批量、要不要做界面——每一个都能吵很久。

项目实际面对三类人：

1. **复核者**：对抗组、教师、组内验证者。他不产出结论，只判断别人的结论能不能站住；
2. **分析者**：本组实现者、初学安全的学生。他关心规则为什么这样写、改了会不会炸；
3. **被审计方**：样本提供方。他关心结论有没有越权。

还有一个隐性用户：**未来的自己**。三个月后回来看这个项目，能不能靠文档恢复上下文。

## 决策

**主用户 = 复核者。** 次用户 = 分析者。被审计方是约束条件，不是功能使用者。

具体落到设计上：

- 报告的默认读者是"要抽查三条结论的人"，不是"想快速看个总分的人"——所以报告按结论分档组织，每条带坐标与证据 ID，不设"安全评分"；
- 所有结论必须先能被机械核对，再谈表达——所以"已确认"的门槛是钉证据成功，不是模型置信度高；
- 不服务"批量扫描农场"：没有任务队列、没有并发调度、没有扫描进度条；
- 不服务"非技术用户"：没有 GUI，不解释基础概念；
- 明确不服务 CI 自动评分：评分必须在人签署之后（ADR-0009）。

## 理由

- 课程的评价链条是 **Agent 审查 → 学生签署 → 教师复评**，三环都在"复核"，没有一环在"批量扫描"；
- 复核者的痛点最硬：他要在不信任你的前提下验证你，任何"信我"的设计对他都无效；
- 分析者的需求（规则口径、回归）可以由同一套文档满足，不需要单独做产品形态；
- 把复核者当主用户，会自然导出"证据优先于召回""诚实优先于好看"这两个原则，而它们正是本项目与通用扫描器的差别。

## 后果

- 正面：报告结构、schema、验收项都有一条统一的判断标准——"这对复核者有没有用"；
- 负面：报告的"可读性"不是第一优先级，初次阅读会觉得信息密度过高；对想"一键出结果"的用户不友好；
- 边界：如果未来要服务批量场景，需要另立产品形态，不能在现有报告上叠加，否则两套目标会互相稀释。

## 替代方案（被否）

| 方案 | 否决理由 |
|------|----------|
| 主用户 = 安全工程师（批量扫描） | 会把设计推向召回率与速度，与本课程的证据纪律冲突；且没有真实用户验证 |
| 主用户 = 开发者（自查） | 需要 IDE 集成与低误报率，超出本项目范围 |
| 不做用户定义，按"通用工具"设计 | 直接导致报告既不适合复核也不适合扫描，是当前多数课程项目的通病 |
