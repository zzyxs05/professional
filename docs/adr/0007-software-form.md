# ADR-0007 · 软件形态与交付形态：本地 CLI、单机离线、文件产物

- 状态：已采纳
- 决策人：周宗正（起草）、余俊辉（复核）
- 关联：`requirements.md` REQ-09/REQ-11/REQ-15/REQ-17、`release.md`、`handoff/README.md`

## 背景

项目立项时需要先定一个看起来"不技术"、但影响后面所有设计的问题：**这个东西以什么形态交出去？**

课程场景的约束是具体的：

1. 教师与对抗组要在**自己的机器**上复核，不能假设有服务器、数据库、账号体系；
2. 评分要看"同一输入是否得到同一结论"，部署越复杂，复现越不可信；
3. 被测样本属于敏感数据，不应经过任何第三方服务；
4. 组内两人要能各自独立跑、独立验证。

候选形态有四种：本地 CLI、Web 服务、桌面 GUI、IDE/CI 插件。

## 决策

**本地 CLI 工具 + 文件产物**，不提供服务端、不提供 GUI、不注册系统服务。

具体形态：

- 唯一入口 `cli.py`，子命令 `analyze / register / evaluate / summary / reset`；
- 输入是本地 APK 路径，输出是目录（`report.md` + `report.json` + `evidence/`）；
- 零第三方运行时依赖（仅 Python 标准库），可执行文件随仓库携带（apktool jar）；
- 机器可读产物是 `report.json`，供评价器与脚本消费；
- 交付即仓库克隆：`git clone` → `python cli.py analyze ...`。

## 理由

- **可复现优先**：CLI 的输入输出都是文件，版本、哈希、命令都能写进文档；Web 服务的状态在数据库和会话里，复现要额外描述环境。
- **合规优先**：样本不出本机。Web 形态要么本地起服务（多一层无收益的复杂度），要么上传（直接违反数据边界）。
- **评分场景匹配**：教师核查的动作是"打开仓库、跑一条命令、看报告"，不是"注册账号、上传文件"。
- **评价器需要机器接口**：四状态输出与引用校验都吃 JSON，CLI 天然满足；GUI 反而要把这层再拆出来。
- **两人协作成本最低**：不需要部署、不需要联调环境，`git pull` 即可。

## 后果

- 正面：交接包可以写成几条命令；任何机器只要能跑 Python 就能复现；证据目录结构稳定。
- 负面：没有图形界面，非技术用户不可用（已列入"不服务"）；批量分析要靠脚本自行循环，不提供任务队列；报告的可视化程度低。
- 约束：任何"加个网页看报告"的需求，都必须先回答"它是否破坏离线与可复现"，否则不做。

## 支撑证据

| 证据 | 位置 | 说明 |
|------|------|------|
| 入口实现 | `cli.py` | 五个子命令，无网络监听、无服务进程 |
| 复现命令 | `handoff/README.md` §1—§2 | 克隆后直接跑，无需安装 |
| 端到端验收 | `scripts/e2e.py` | 全样本受理 + 两次运行一致性 |
| 依赖声明 | `release.md` §1 | Python 3.8+ / Java 8+，无 pip 依赖 |
| 合规声明 | `release.md` §5 | 只读不执行、分析链路零网络调用 |

## 替代方案（被否）

| 方案 | 否决理由 |
|------|----------|
| Web 服务（上传→分析→网页报告） | 样本离开本机，违反数据边界；部署与账号体系对本课程无增量价值；复现要描述服务状态 |
| 桌面 GUI | 开发成本高，评审时无法脚本化验证；报告已经是文件，GUI 只是壳 |
| IDE / CI 插件 | 绑定特定宿主，教师机器不一定有；且"自动跑"与"人工签署"的纪律冲突（见 ADR-0009） |
| 纯库（不提供 CLI） | 复核者要写代码才能用，违背"打开仓库就能验"的目标 |
