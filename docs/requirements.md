# requirements · 需求说明（稳定层）

> 交付类：brief / design 之间的需求层｜版本：v1.0
> 定位：本文档回答"**谁、在什么场景下、需要系统保证什么**"，不回答"怎么实现"。
> 稳定性：UN / REQ 编号属于项目稳定部分，变更必须记 `changes.md` 并说明影响；实现细节（规则怎么扩、模型换哪个）不进本文档。
> 上游：`research/apk-audit-landscape.md`（调研推导）｜下游：`specification.md`（规格）、`acceptance-matrix.md`（验收）

---

## 1. 角色与利益相关者

| 角色 | 是谁 | 关心什么 | 不关心什么 |
|------|------|----------|-----------|
| **主用户：复核者** | 对抗组、教师、组内验证者 | 这条结论能不能按坐标直达原文；证据是否真存在；没查的部分有没有说 | 工具有多少条规则、界面好不好看 |
| **次用户：分析者** | 本组实现者、安全方向初学者 | 为什么报这一条；规则的误报口径是什么；改了规则会不会破坏基线 | 报告的排版 |
| **间接受众：被审计方** | 样本提供方（课程内为自建样本） | 结论有没有越权断言；有没有把"疑点"写成"事实" | 内部实现 |
| **不服务** | 批量样本农场、CI 流水线、非技术用户 | — | — |

> "不服务"是明确的范围声明，不是能力贬低。理由见 ADR-0008。

## 2. 使用场景

### 场景 A：对抗组复核（主场景）

对抗组拿到本组交付的 `report.md` 与 `handoff/`，要在**不重跑**的前提下判断某条结论是否成立。
他们需要：结论 → 坐标 → 证据文件 → 原文片段，四步可达；并且能看出这条是"已确认"还是"待复核"。

### 场景 B：规则变更后的回归

实现者修改一条规则的检测点或阈值，需要知道：历史报告会不会被改写、靶场 84 判点是否仍然一致、哪些样本的结论会翻转。
他们需要：版本绑定 + 真值一致性脚本 + 变更影响记录。

### 场景 C：工具链不完整的降级运行

在只装了 Python、没有 Java/apktool 的机器上跑分析。
需要：M/S 类规则照常出结论，P/C/N 类明确列入"未覆盖"，而不是静默跳过或报错崩溃。

## 3. 用户需求（UN）

| ID | 需求 | 谁需要 | 痛点（不做会怎样） | 满意条件 |
|----|------|--------|-------------------|----------|
| **UN-01** | 每条结论可定位到代码原文 | 复核者 | 只能相信报告的文字，无法验证；等于把审计变成"听汇报" | 按坐标打开文件即可看到对应指令/属性，不需要重跑工具 |
| **UN-02** | 结论区分"已确认 / 待复核 / 无法判定" | 复核者、被审计方 | 疑点被当成事实，或失败被写成通过 | 三档在报告与 JSON 中都是显式字段；升级有证据门槛 |
| **UN-03** | 每份报告声明覆盖范围 | 复核者 | "未发现"被误读为"安全" | 报告含 checked / not_checked 清单与原因；"未发现"必附声明 |
| **UN-04** | 模型的输出不能直接成为结论 | 全角色 | 结论不可复现、无法追责；模型编造无人拦 | 模型只出现在提疑/复核位置；升级必须经过机械证据核对 |
| **UN-05** | 工具缺失时降级并如实声明 | 分析者 | 少跑了一半规则却看不出来 | 缺 apktool → P/C/N 类进未覆盖；缺模型 → B 通道声明未运行 |
| **UN-06** | 同输入 + 同版本 → 同一份报告 | 复核者、教师 | 同一份材料两次跑出不同结论，无法评分 | A 通道逐字段一致；B 通道波动范围在报告中声明 |

## 6. 明确不做（out of scope）

| 不做 | 原因 | 依据 |
|------|------|------|
| 加固样本分析 / 脱壳 | 静态分析在壳面前失效，做了也是假结论 | 调研 §2.4；ADR-0002 |
| 动态分析 / 执行样本 | 引入运行风险，违反"只读不执行" | 总档 §10 |
| 真实第三方应用的公开结论 | 合规边界，需教师批准 | 总档 §10 |
| MASVS 全量覆盖 | 只做静态可判、有机械证据的部分 | 调研 §4 |
| 规则数量竞赛 | 每条规则要配证据模板与真值，否则是噪声 | 总档 §5.2 |
| GUI / Web 服务 | 交付形态是本地 CLI，见 ADR-0007 | — |

## 7. 需求变更规则

1. UN 层变更 = 范围变更，必须说明"谁的哪个痛点没被满足"，并评估是否影响已交付的验收项；
2. REQ 层变更 = 能力变更，必须同步 `specification.md`、`acceptance-matrix.md` 与规则包版本；
3. 只改实现、不改 UN/REQ 的，走 ADR 或 `changes.md`，不需要动本文档；
4. 任何变更都要回答一个问题：**已有的证据还成立吗？** 不成立的，旧报告保留原解释，新结论绑定新版本。
