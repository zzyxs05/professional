# 领域调研：APK 静态安全审计的现状与本项目定位

> 交付类：research（需求与规格的支撑材料）｜版本：v1.0
> 调研问题：现有工具已经能做什么、它们在"结论可复核"这件事上缺什么、本项目应该补哪一段。
> 写作纪律：**每条外部事实都带来源与访问日期**；无法核实的数字不写；未做的评测在 §7 如实声明。

---

## 0. 结论先行

1. **"能不能扫出问题"已经不是一个空白领域。** MobSF、apkleaks、Androguard、APKiD 各自覆盖了静态审计的一段，成熟度和社区规模都远超单个课程项目。
2. **空白不在检测能力，在"结论的可复核性"。** 现有工具普遍输出"发现了什么"，但不强制输出"这条结论定位到哪一行、哪条规则判的、覆盖了哪些没覆盖哪些、这个结论是确认还是疑点"。这一层是人工补的，而人工补的部分无法被第三方按同一口径复算。
3. **LLM 的位置被两类错误用法夹住了。** 一类是让模型直接下结论（不可复现、会编）；一类是把模型生成的长文当报告（看着像分析，实际没有证据锚点）。可行的位置只剩中间那一层：**模型提疑，确定性规则钉证据**。
4. 本项目因此不做"又一个扫描器"，做的是**审计结论的证据层**：规则可冻结、结论分档、坐标可直达、覆盖必须声明。这个定位直接决定了需求文档里的 6 条用户需求（见 `../requirements.md`）。

## 2. 现有工具的四类形态

### 2.1 平台型：MobSF

- 定位：一体化的移动应用安全测试框架，静态 + 动态 + 恶意行为分析，覆盖 Android / iOS / Windows。
- 形态：Web 应用（Docker 部署），提供 REST API 与 `mobsfscan` CLI，可接 CI/CD。
- 静态侧能力：反编译 APK/AAB，检查硬编码密钥、不安全存储、弱加密、危险权限、导出组件、SSL/TLS 配置，并把发现映射到 OWASP MASVS / MASTG。
- 许可：GPL-3.0。
- 对本项目的意义：**它证明了"MASVS 映射 + 报告"是行业惯例**，本项目规则表的分类方式（M/P/S/C/N）可以对齐到 MASVS 组，而不是自创一套分类。
- 来源：<https://github.com/MobSF/Mobile-Security-Framework-MobSF>（访问日期见 §8）；MASVS 映射说明见 <https://mas.owasp.org/MASVS/>。

### 2.2 单点提取型：apkleaks

- 定位：只做一件事——从 APK 里提取 URI、端点、硬编码密钥。
- 实现：调用 jadx 反编译，再用 50+ 条正则匹配；规则可用 JSON 自定义（`-p`）；输出 text / JSON。
- 明确边界：**正则命中只说明"字符串长得像密钥"**，不确认密钥是否有效，结果仍需人工 triage。
- 对本项目的意义：这是"检测"与"结论"之间差距最清楚的例子。本项目 R-STR-01 采用"形式匹配即事实、示例值照报"的口径，正是承认这一点：报告事实，不冒充有效性判定。
- 来源：<https://github.com/dwisiswant0/apkleaks>（访问日期见 §8）。

### 2.3 库/框架型：Androguard

- 定位：纯 Python 的 Android 文件处理库，可解析 DEX/ODEX、APK、二进制 XML、resources.arsc，反汇编字节码，提供 CLI 与 Python API。
- 形态：既可当工具，也可当库被别的流水线调用；有 `androguard axml` / `arsc` / `sign` / `cg` 等子命令。
- 对本项目的意义：说明"自研解析 + 库解析"是常见组合。本项目选择自研 AXML/DEX 直读（零依赖）+ apktool 反汇编，属于同一思路的一个具体取舍，理由见 ADR-0002。
- 来源：<https://androguard.readthedocs.io/en/stable/>（访问日期见 §8）。

### 2.4 指纹型：APKiD

- 定位：识别 APK 是"怎么造出来的"——编译器、加固壳、混淆器、反虚拟机/反调试痕迹。
- 实现：YARA 规则 + DEX 感知模块，规则集社区维护；输出按 dex / so 分文件列出。
- 关键边界：**它是样本预处理/分流工具，不是漏洞检测工具**。识别出"有壳"意味着后续静态分析的可信度下降，而不是"这个应用有问题"。
- 对本项目的意义：直接支撑本项目的范围声明——**不含加固样本**。这不是回避，而是承认静态分析在加固面前的失效边界（见 `../specification.md` §1 与 `../release.md` I-3）。
- 来源：<https://github.com/rednaga/APKiD>（访问日期见 §8）；OWASP MASTG 的使用说明：<https://mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0165/>。

### 2.5 反编译型：jadx

- 定位：DEX → Java 源码的反编译器，常被 MobSF、apkleaks、Androguard 当作前端。
- 边界：反编译失败在真实样本上不可忽略；失败即整段代码不可见。
- 对本项目的意义：本项目语义规则改用 smali（字节码 1:1 直译），规避"反编译失败率"，代价是规则要按 smali 模式写。取舍记在 ADR-0002。
- 来源：<https://github.com/skylot/jadx>（访问日期见 §8）。

## 4. 标准侧：MASVS 的八个控制组与本项目的覆盖

OWASP MASVS 把移动应用安全控制分为八组：STORAGE、CRYPTO、AUTH、NETWORK、PLATFORM、CODE、RESILIENCE、PRIVACY。

本项目的 14 条规则落点：

| MASVS 组 | 本项目对应 | 覆盖程度 |
|----------|-----------|----------|
| MASVS-PLATFORM | R-MAN-01（导出组件）、R-MAN-05（敏感广播）、R-PERM-02（非交互组件） | 部分 |
| MASVS-NETWORK | R-MAN-03（明文流量）、R-STR-02（内网端点）、R-NET-01/02（证书校验/SSL 错误） | 较好 |
| MASVS-CODE | R-CODE-01（动态加载）、R-CODE-02（WebView 组合） | 部分 |
| MASVS-STORAGE | R-STR-01（硬编码凭据） | 很弱（不做文件存储/数据库检查） |
| MASVS-CRYPTO | 无 | 未覆盖 |
| MASVS-AUTH | 无 | 未覆盖 |
| MASVS-RESILIENCE | 无（加固样本直接排除） | 明确不做 |
| MASVS-PRIVACY | 间接（危险权限 R-MAN-02） | 很弱 |

**这张表要说清一件事：本项目不是"移动应用安全的全量检查工具"。** 它只覆盖静态可判、且能给出机械证据的那一部分。报告里的覆盖声明必须体现这个边界，否则"未发现"会被误读成"安全"。

来源：<https://mas.owasp.org/MASVS/>（访问日期见 §8）。

## 5. 空白点：三个没有被现有工具解决的问题

### 5.1 结论与证据之间没有强制绑定

MobSF 的报告有文件与行号，但它是"报告级"的证据；apkleaks 只给匹配串，不给上下文；APKiD 给的是指纹不是漏洞。三者都没有强制"每一条结论必须能按坐标直达原文，且原文在证据库里存过、有哈希"。

对本项目的推导：**证据 ID + 坐标 + 原文片段三件套必须是 schema 的必填项，不是报告的装饰。**

### 5.2 不确定性没有表达位置

现有工具的输出基本是二值的：报了 / 没报。但静态分析里大量结论的真实状态是"有结构，但没有行为证据"（例如"存在定时器 + 存在录音 API"≠"半夜在录音"）。工具不表达这一层，使用者就只能自己脑补，脑补的结果无法复核。

对本项目的推导：**三档结论（已确认 / 待复核 / 无法判定）不是保守，是唯一诚实的表达方式**；档位上限要写进规则契约，由融合层强制执行（ADR-0003）。

### 5.3 LLM 介入没有责任边界

OWASP Top 10 for LLM Applications 把 Overreliance（过度依赖模型输出、缺少批判性复核）列为独立风险项，指出未加验证地信任模型输出会导致错误决策与安全漏洞。

在静态审计场景里，这对应两种失败：
- 让模型直接给"这个 APK 安全/不安全"——不可复现，且模型的判断没有证据锚点；
- 让模型自由撰写报告——文字通顺，但数字、结论、引用都可能是编的。

对本项目的推导：**模型只允许出现在"提疑"和"复核"两个位置，且输出必须落到固定 schema；升级为"已确认"只能走机械钉证据（ADR-0004）。** 模型原声另设 observations 区，与结论分离。

来源：<https://owasp.org/projects/top-10-for-large-language-model-applications>（LLM09 Overreliance；访问日期见 §8）。

## 6. 从调研到需求

调研结论直接推导出 6 条用户需求（编号与 `../requirements.md` 一致）：

| 调研发现 | 推导出的用户需求 |
|----------|------------------|
| 工具能扫，但结论不可复核（§5.1） | UN-01 复核者要能按坐标直达原文，不重跑 |
| 不确定性无表达位置（§5.2） | UN-02 报告必须区分确认/疑点/无法判定 |
| "未发现"会被误读为安全（§4） | UN-03 每份报告必须带覆盖声明 |
| LLM 直接下结论不可信（§5.3） | UN-04 模型只能提疑，升级要靠机械证据 |
| 工具链缺失会导致整段不可用（§2.5） | UN-05 缺工具时要降级并声明，不能静默 |
| 结论要能被第三方复算（§5.1） | UN-06 同一输入 + 同一版本 → 同一份报告 |

这 6 条是稳定需求；规则集怎么扩、模型换哪个，都属于实现层变更，不改这 6 条。

## 7. 本调研的局限（如实声明）

1. **没有做横向实测。** 上表的能力判断来自各工具公开文档，不是在同一批样本上跑出来的对比数据。若要支撑"本项目优于 MobSF"这类结论，需要另做实验——本报告不主张这种结论。
2. **样本仅有自建的 6 个。** 无法外推到真实应用分布；84/84 只证明"在标定样本上与真值一致"，不证明真实场景的检出率。
3. **未覆盖加固与动态分析。** 这是范围选择，不是能力评价。
4. **工具版本会漂移。** MobSF、apkleaks、APKiD 均在活跃维护，本报告的能力描述以 §8 所列访问日期的文档为准；后续引用需重新核对。
5. **没有引用学术论文的量化数据。** 避免把未读过的论文结论当支撑材料——这正是本课程反对的"没有对应支撑材料的表述"。
