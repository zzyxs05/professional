## 3. E3 · 受控 Red Team

### 3.1 规矩

- 只针对**自建样本与本地分析**，不构造针对真实应用的攻击；
- 清单是**假设，不是已确认缺陷**。没实跑就不能写成缺陷；
- 从 16 条里挑 **3—5 条**，优先 A-01 / A-05 / A-08 / A-13 / A-16；
- **确认的阻断问题必须报**，不设数量上限，不因"显得问题多"而隐瞒。

### 3.2 Finding 六要素（缺一项就不算 Finding）

| 字段 | 要求 |
|---|---|
| 目标版本 | 规则包版本 + RUN id + 一句 commit 记录（`本测试基于 commit <short-hash>`） |
| 前置条件 | 样本构造方式、运行环境（Java/apktool/Python 版本） |
| 最小复现 | **一条命令 + 样本 sha256** |
| 实际 / 预期 | 分开写，不许合并成一句 |
| 证据 | 报告坐标 + 原文片段 + 日志/截图 |
| 影响 | 漏报 / 误报 / 档位错 / 措辞升级，四选一 |
| 修复回归 | 他修完，你用**同一条命令、同一 commit** 复跑 |

### 3.3 造样本的路线（本机已验可走，不需要 Android SDK）

`apktool d` 一个 `lab/apks/bad0x.apk` → 改 `AndroidManifest.xml` 或 smali → `apktool b` 回编译 → `jarsigner` 签名（Java 11 自带）。改了哪个文件、加了哪条指令，都要写进"前置条件"，否则不算最小复现。

### 3.4 建议优先构造的四条（理由见 §6）

| # | 规则 | 造什么 | 为什么值得先打 |
|---|---|---|---|
| A-13 | R-NET-01 | `checkServerTrusted` 方法体只有 `Log.d(...)`，无 throw 无校验 | 判据写死"空方法体（无 invoke）"，加一条日志就绕开。**这是判据定义的缝，不是能力边界，对方没法用"设计取舍"挡** |
| A-02 | R-MAN-02 | 敏感权限改用 `<uses-permission-sdk-23>` 声明 | 改一行 manifest，成本最低的漏报验证 |
| A-04 | R-MAN-05 | 静态 Receiver 加 `android:enabled="false"` | 判据没排除 enabled=false，大概率误报 |
| A-05 | R-PERM-01 | 调度原语与敏感 API 分处两个自有类 | **一鱼两吃：E3 出 Finding → 正好喂 E2 的 CHG-004** |

### 3.5 会被挡回来的四条（对方已声明不修，`e3_attack_surface.md` §4）

字符串拼接/加密凭据、加固样本、native 内部逻辑、反射实际目标。这四条提 Finding 的**唯一有效角度**是：报告里的覆盖声明到底写了没有、写得够不够清。覆盖边界没写清，仍算缺陷；写清了，就是设计取舍。

### 3.6 B 通道已可用，A-16 现在能真打

`key.txt` 配好后 B 通道实跑成功（deepseek-flash，8 次调用，42 秒）。A-16（多位置诱导文本）之前只能验 A 通道不受影响，现在**可以验 B 会不会被诱导压制疑点**——这是 OWASP LLM01（提示注入）类问题，确认即阻断级 Finding。
